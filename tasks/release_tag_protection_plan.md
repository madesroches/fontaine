# Release Tag Protection Plan

**GitHub Issue**: https://github.com/madesroches/fontaine/issues/758

## Overview
Release tags are unprotected: anyone with push access can create, move or delete a `v*` tag, and
`release.yml` also triggers on non-`v` version tags that then fail at the signing job. Add a tag
ruleset (kept in the repo as importable JSON), align the workflow's tag filter with the
`release-signing` environment's `v*` policy, and fail the `plan` job early when the tagged commit
is not on `main`.

## Current State
- `.github/workflows/release.yml:62-63` triggers on `'**[0-9]+.[0-9]+.[0-9]+*'`, so `foo/1.2.3` or
  `1.2.3` start the pipeline; the `sign` job (environment `release-signing`, line ~299) only admits
  `v*` tags, so those runs build everything and then fail.
- The `plan` job derives `sign-version` with `${GITHUB_REF_NAME#v}` and checks out with
  `persist-credentials: false`.
- `CONTRIBUTING.md` "Releasing" (step 5 says tag on the merge commit on `main`) and the
  "Signing keys and environments" table document the environment policy. No ruleset exists
  (`gh api repos/madesroches/fontaine/rulesets` returns `[]`).
- `.github/scripts/check-pinned-actions.sh` and `rust/Cargo.toml` `allow-dirty = ["ci"]` mean the
  hand-adapted workflow is not regenerated by dist.

## Design
1. **Tag filter.** Replace the pattern with `'v[0-9]+.[0-9]+.[0-9]+*'` (GitHub glob: `+` is "one
   or more of the preceding character", so it matches the `v`-prefixed SemVer family dist
   accepts, such as `v0.1.0-rc.1`). Update the adjacent dist comment, which lists unprefixed
   example tags, to say only `v`-prefixed tags run.
2. **Reachability gate.** New step in `plan`, run only for tag pushes, after checkout:
   `git fetch --no-tags origin main` then
   `git merge-base --is-ancestor "$GITHUB_SHA" origin/main`, failing with an `::error::` that
   names the tag. Checkout is shallow, so ancestry needs history: the `plan` checkout gets
   `fetch-depth: 0`, which already fetches `main`, making the extra fetch unnecessary.
3. **Ruleset.** Commit `.github/rulesets/release-tags.json`, a GitHub ruleset export:
   `target: tag`, `enforcement: active`, include `refs/tags/v*`, rules `creation`, `update`,
   `deletion`, and `bypass_actors` for the repository admin role only (so the maintainer can
   still tag). It is applied by the maintainer with
   `gh api repos/madesroches/fontaine/rulesets --input .github/rulesets/release-tags.json`; the
   chain does not apply it (a repo-settings change, not a code change).

## Implementation Steps
1. Edit `.github/workflows/release.yml`: tag filter, header comment, `fetch-depth: 0` on the
   `plan` checkout, reachability step.
2. Add `.github/rulesets/release-tags.json`.
3. Update `CONTRIBUTING.md`: Releasing step 5 mentions the workflow rejects tags not on `main`;
   add a "Tag ruleset" paragraph under "Signing keys and environments" with the apply command.
4. Add a `CHANGELOG.md` Unreleased entry.

## Trade-offs
- Ruleset as committed JSON vs. clicking in the UI only: the JSON is reviewable and reproducible;
  it is inert until applied.
- Reachability in the workflow vs. the ruleset: rulesets cannot express "commit is on main" for
  tags, so the workflow checks it.

## Testing Strategy
No Rust code changes. Automated: `.github/scripts/check-pinned-actions.sh` still passes; the
ruleset JSON parses (`jq . .github/rulesets/release-tags.json`); the `plan` job's PR run (`dist
plan`) stays green. The ancestry command is verified locally against a temp repo with a tag on
and off the main branch.

## Manual Verification
After the maintainer applies the ruleset: `git push origin :refs/tags/v0.0.0-test` on a throwaway
tag by a non-admin is rejected. Not automatable: needs a second account and live repo settings.

## Open Questions
- Should the bypass actor be the admin role or only the maintainer's user? Admin role is the only
  actor type usable by a personal-repo ruleset via API without a user id.
