# Release Signing Plan

**GitHub Issue**: https://github.com/madesroches/fontaine/issues/425

## Overview

Every archive Fontaine publishes, on both update channels, gets a detached minisign (ed25519)
signature made in CI with a Fontaine-owned key for that channel: `release` follows tagged
releases, `dev` publishes a build after every push to `main`. Each private key lives in its own
protected GitHub Environment that only the signing job can reach. Publication fails unless every
archive has a signature that verifies against the public key checked into the repository. A
small verification module in the `fontaine` crate, built on `minisign-verify`, is the one
verifier that the installers (#176), the automatic updater and `fontaine update` (#175) will
call. This issue ships that module, not its callers. The issue blocks #175, #176 and the first
release tag (#109).

## Current State

- `.github/workflows/release.yml` is the cargo-dist 0.32.0 workflow, adapted by hand for the
  `rust/` workspace (`allow-dirty = ["ci"]` in `rust/Cargo.toml:123`). A tag push runs `plan`,
  then `build-local-artifacts` (one archive per target, plus a `.sha256` for each),
  `build-global-artifacts` (the combined `sha256.sum`), then `host`, which runs
  `gh release create` and publishes immediately, then `announce`. PRs run only `plan`. The whole
  workflow has `contents: write`, and no job uses a GitHub Environment.
- Targets (`rust/Cargo.toml:115`): `x86_64-unknown-linux-gnu`, `aarch64-apple-darwin`,
  `x86_64-apple-darwin`, `x86_64-pc-windows-msvc`. Archives are `.tar.xz` on Unix and `.zip` on
  Windows, named `fontaine-<target>.<ext>`.
- There is no dev channel, no signing, no attestations and no installers (`installers = []`).
- No crate depends on ed25519 or minisign. `sha2 = "=0.11.1"` is in the workspace.
- `CONTRIBUTING.md` §Releasing (line 60) is the maintainer's release checklist.
  `tasks/design/platforms.md` §Releases (line 27) is the design record.
- The README install section (`README.md:14`) says to unpack the archive. It says nothing about
  verifying it.
- No updater exists (#175), and no installers either (#176).

## Design

### Keys and trust root

- There are two minisign keypairs, `release` and `dev`, generated by the maintainer with the
  stock `minisign -G`. Each secret key is password-protected.
- The public keys are checked in as `rust/fontaine/keys/release.pub` and
  `rust/fontaine/keys/dev.pub`, in minisign's own `.pub` format (an `untrusted comment:` line,
  then the base64 key line). The same files feed three consumers: `include_str!` into the
  binary, `minisign -V -p` in CI, and the manual-verification docs.
- Until the maintainer bootstraps the keys, each file holds only a comment line
  (`untrusted comment: fontaine <channel> key not yet bootstrapped`). The loader reads such a
  file as "no key for this channel", and every verification against that channel fails with
  `NoKeyForChannel`. Signing jobs fail too, because their post-sign check uses the same file.
  So nothing can be published with an unbootstrapped channel. Production keys are never
  generated by an automated run; bootstrapping is a maintainer step (see Key management).
- A unit test checks the shipped key files: each one is either a valid key or the bootstrap
  placeholder. When both hold keys, their key IDs must differ, because a shared key would let a
  dev-key compromise authorize release artifacts.

### Trusted comment binding

The signer sets the signed trusted comment to:

```
fontaine-signature v1 channel=<release|dev> file=<archive basename> version=<cargo version> commit=<git sha>
```

The verifier requires the `v1` prefix, `channel` equal to the requested channel, and `file`
equal to the basename being verified. Separate keys already keep the channels apart. The `file`
check stops a validly signed archive from being swapped in for another target. `version` and
`commit` are returned to the caller: #175's updater uses them for its downgrade and
channel-switch rules, and this module enforces neither.

### Verification module (`rust/fontaine/src/release_signature.rs`)

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum Channel { Release, Dev }

pub struct TrustedKeys { release: Option<PublicKey>, dev: Option<PublicKey> }

impl TrustedKeys {
    /// The keys compiled into this binary.
    pub fn embedded() -> &'static TrustedKeys;
    /// Parse `.pub` file contents (used by `embedded()` and by tests with disposable keys).
    pub fn from_pub_files(release: &str, dev: &str) -> Result<TrustedKeys, KeyFileError>;
}

pub struct Verified { pub channel: Channel, pub file: String, pub version: String, pub commit: String }

#[derive(Debug, thiserror::Error)]
pub enum VerifyError {
    NoKeyForChannel(Channel),
    MissingSignature,
    MalformedSignature(#[source] minisign_verify::Error),
    WrongKey { channel: Channel },   // key ID is not this channel's key (e.g. the other channel's)
    BadSignature(#[source] minisign_verify::Error),
    MalformedTrustedComment,
    ChannelMismatch { expected: Channel, found: String },
    FileMismatch { expected: String, found: String },
    Io(#[source] std::io::Error),
}

pub fn verify_file(keys: &TrustedKeys, channel: Channel, archive: &Path,
                   signature: Option<&str>) -> Result<Verified, VerifyError>;
```

- The function takes the signature text as `Option<&str>`, so a missing signature has its own
  variant instead of turning into an I/O error at a guessed path. Callers fetch `<archive>.minisig`
  themselves.
- It hashes the archive in a stream (`minisign_verify::StreamVerifier`), because archives are
  tens of MB.
- The error enum is typed because callers dispatch on it: the updater reports why, and CI tests
  each class. Only `Verified` means success. Every other outcome, including I/O, is a failure,
  and the caller must leave the installed binary untouched.
- There is no prehashed or legacy mode. minisign's legacy (non-prehashed) signatures are
  rejected as malformed, because CI always signs prehashed (minisign's default since 0.8).

### CI signing tool

- The signing and verification jobs use the upstream `minisign` CLI at a pinned version: the
  release tarball from `jedisct1/minisign`, checked against a pinned sha256 before it runs.
- `.github/scripts/release-sign.sh <channel> <dir>` signs every `fontaine-*.tar.xz` and
  `fontaine-*.zip` in `<dir>`, using the secret key and password from the environment
  (`MINISIGN_SECRET_KEY`, `MINISIGN_PASSWORD`, written to a `0600` temp file and removed on
  exit). It then runs the verify script on its own output. With zero archives it exits non-zero.
- `.github/scripts/release-verify.sh <channel> <dir> <pubkey>` checks the following, and fails
  on the first error:
  - every archive has a `.minisig`, and no `.minisig` lacks its archive;
  - `minisign -V -p <pubkey> -m <archive>` passes;
  - the trusted comment has the exact binding above for `<channel>` and that basename;
  - every `.sha256` matches its archive;
  - at least one archive is present.

  The same script is the release check and the CI test subject, so "verified before
  publishing" and "covered by tests" are one code path.

### `release` channel workflow (`.github/workflows/release.yml`)

```
plan ─▶ build-local-artifacts ─▶ build-global-artifacts ─▶ sign (env: release-signing,
                                                                 required reviewer, tags v*)
      ─▶ host (draft release with archives + .minisig + checksums)
      ─▶ verify-draft (gh release download the draft; release-verify.sh vs keys/release.pub)
      ─▶ publish (gh release edit --draft=false) ─▶ announce
```

- The build jobs are unchanged and reference no environment, so the signing secrets are never
  in scope for them. PRs still run only `plan`.
- `sign` is a new job with `environment: release-signing`. It downloads the `artifacts-*`
  workflow artifacts, installs the pinned minisign, runs `release-sign.sh release`, and uploads
  the `.minisig` files as `artifacts-signatures`. It checks out the repository only to read the
  scripts and `keys/`, with `persist-credentials: false`. It runs no build tools and no code from
  the artifacts.
- `host` keeps `dist host`, but creates the release with `gh release create --draft`, adding the
  signature files.
- `verify-draft` downloads every asset of the draft (`gh release download <tag>`), so it checks
  exactly what users will fetch, and runs `release-verify.sh release`.
- `publish` flips the draft to published, only after `verify-draft` succeeds. If anything fails,
  the draft stays a draft and nothing is public.
- Per-job `permissions`: `contents: read` by default. Only `host` and `publish` get
  `contents: write`.

### `dev` channel workflow (`.github/workflows/dev.yml`, new)

```
push to main ─▶ build (dist build --artifacts=local per target, no tag, no secrets)
             ─▶ global (sha256.sum) ─▶ sign (env: dev-signing, main only, no reviewer)
             ─▶ draft prerelease dev-<run_number> ─▶ verify-draft (vs keys/dev.pub)
             ─▶ publish (--draft=false, stays --prerelease, never "latest")
```

- The build matrix comes from `dist plan` in the same way as in `release.yml`. The trusted
  comment's `version` is `<cargo version>-dev.<run_number>+<short sha>`. #175 owns how the
  updater orders dev builds; this field only gives it the data.
- Draft, then verify, then publish is the "verify before visible to updaters" gate. A draft
  release is invisible to unauthenticated API clients, so an updater can never see an
  unverified dev build.
- The whole workflow runs only when the repository variable `FONTAINE_DEV_CHANNEL` is `enabled`
  (job-level `if:` on the first job). This keeps `main` green until the maintainer has created
  the `dev-signing` environment and bootstrapped the dev key. When the variable is not set,
  nothing is built and nothing is published, so skipping can never publish an unsigned
  artifact.
- `concurrency: dev-channel` with `cancel-in-progress: false` serializes publication.
- Old dev prereleases are not pruned here; see Decisions.

### Environments (maintainer configuration, documented)

| Environment | Secrets | Deployment rule | Reviewers |
|---|---|---|---|
| `release-signing` | `MINISIGN_SECRET_KEY`, `MINISIGN_PASSWORD` (release key) | tags matching `v*` only | maintainer, required |
| `dev-signing` | same names (dev key) | branch `main` only | none |

Environment secrets reach only jobs that name the environment, and the deployment rule refuses
runs from other refs. That includes PRs: a `pull_request` run's ref is `refs/pull/...`. These
settings live in GitHub, not in the repository, so configuring them is a maintainer step.

### Key management (documented in `CONTRIBUTING.md`)

- **Bootstrap**: for each channel, run `minisign -G -p <channel>.pub -s <channel>.key`, commit the
  `.pub` file over the placeholder, put the key file's content and the password into that
  channel's environment secrets, then move the secret key offline (an encrypted backup) and
  delete the working copy.
- **Rotation (per channel)**: generate the new pair. Release N, signed with the old key, embeds
  the new public key. After N is published, swap the environment secret. N+1 and later are
  signed with the new key. Binaries older than N cannot verify N+1, so they must update to N
  first or reinstall; #175 owns stepping through N. A new key is therefore always introduced by
  an artifact signed with the old key for that channel.
- **Revocation and recovery (compromise or loss)**: there is no online revocation list. Remove the
  environment secret at once, publish a security advisory, generate a new pair, and ship a
  release embedding it. If the old key was compromised, users must reinstall through the HTTPS
  installer or a manual download verified against the new key in the repository, because an
  update signed with the compromised key proves nothing. A dev-key compromise never affects
  `release`.

## Implementation Steps

1. **Placeholders.** Add `rust/fontaine/keys/release.pub` and `rust/fontaine/keys/dev.pub`
   holding the bootstrap placeholder comment line.
2. **Dependencies.** In `rust/Cargo.toml`, add `minisign-verify = "=0.3.0"` (runtime) and
   `minisign = "=0.10.0"` (dev-only, for disposable test keys). Run `cargo deny check`, and if
   their licenses (MIT / ISC) are not yet allowed, update `rust/deny.toml`.
3. **Verification module.** Write `rust/fontaine/src/release_signature.rs` as designed and
   export it from `rust/fontaine/src/lib.rs`. Unit tests use the `minisign` crate to make
   disposable keys and signatures at test time:
   - a valid signature returns `Verified` with the parsed fields;
   - a missing signature returns `MissingSignature`;
   - malformed signatures (truncated base64, garbage, an empty string, a legacy non-prehashed
     signature) return `MalformedSignature`;
   - a signature from another key returns `WrongKey`;
   - a signature from the dev key checked on the release channel returns `WrongKey`;
   - a tampered archive returns `BadSignature`;
   - a channel field that differs returns `ChannelMismatch`;
   - a file name that differs returns `FileMismatch`;
   - a trusted comment without the `v1` prefix returns `MalformedTrustedComment`;
   - a placeholder key returns `NoKeyForChannel`;
   - the shipped key files test described under Keys.
4. **Interop test.** `release_signature::cli_interop` is `#[ignore]`d and reads
   `FONTAINE_SIGNING_FIXTURE_DIR`. It verifies files produced by the real `minisign` CLI and
   `release-sign.sh`, so the CLI's output format and the Rust verifier cannot drift apart.
5. **Scripts.** Write `.github/scripts/release-sign.sh` and `.github/scripts/release-verify.sh`
   (bash, `set -euo pipefail`), plus `.github/scripts/install-minisign.sh` for the pinned
   download and sha256 check.
6. **CI coverage (`ci.yml`, Linux job).** Add a "Release signing" step:
   - install minisign and generate a disposable passwordless key, plus a second key that plays
     the wrong-channel key;
   - make dummy archives and their `.sha256` files;
   - run `release-sign.sh`, then `release-verify.sh` and expect success;
   - expect `release-verify.sh` to fail on each mutation: a deleted `.minisig`, a truncated
     `.minisig`, an archive signed by the other key, a tampered archive, an orphan `.minisig`,
     an empty directory and a wrong `--channel`;
   - run `cargo test -p fontaine release_signature -- --ignored` with the fixture directory set.
   Production secrets are never referenced: the job names no environment.
7. **`release.yml`.** Add the `sign`, `verify-draft` and `publish` jobs, make `host` create a
   draft and upload the signatures, and scope permissions per job. Update the hand-adaptation
   header comment.
8. **`dev.yml`.** Add the new workflow as designed.
9. **Docs.** See Documentation.
10. **Master plan.** Add the `Build and release` Decisions lines below, and the `#425` item under
    Release readiness in `## Remaining work`.

## Trade-offs

- **Verifier: `minisign-verify` rather than the full `minisign` crate.** It has zero
  dependencies and does verification only, so no signing or scrypt code ships in the binary.
  The full crate is a dev-dependency only.
- **Signer: the upstream minisign CLI rather than rsign2 or a workspace tool.** It is the
  reference implementation, and manual-verification users run the same tool. A pinned tarball
  with a checked sha256 avoids the drift of distro packages.
- **The CI release check uses the minisign CLI, not the shipped `fontaine` binary.** Using a
  binary to verify the archive it came from is circular. The ignored interop test covers format
  agreement with the Rust verifier, and it needs no new CLI surface.
- **One key per channel, not a key list.** It is simpler, and the rotation procedure still
  introduces each new key through an old-key-signed release. A key list would only shorten the
  window during which old clients must step through N.
- **Draft releases as the visibility gate**, rather than a rolling `dev` release with a pointer
  manifest. It is atomic, the two channels share it, and GitHub hides drafts from
  unauthenticated clients.

## Decisions

- 2026-11-05: Production keys are bootstrapped by the maintainer. The repository ships
  placeholder `.pub` files that make verification and signing fail closed until then.
- 2026-11-05: The installers' call into this verifier ships with #176, and the updater's with
  #175. This issue ships the shared module, the CI signing and verification, and the docs.
- 2026-11-05: GitHub artifact attestations are not enabled here. They stay optional, owned by
  #176 (`github-attestations` in dist), and are never the trust root.
- 2026-11-05: Dev prereleases are not pruned in this issue. Deleting releases and tags from CI
  is a separate, reviewable change (follow-up issue).
- 2026-11-05: `dev.yml` is gated on the repository variable `FONTAINE_DEV_CHANNEL=enabled`, so
  `main` stays green before the dev environment exists. A skipped run publishes nothing.

Lines for the master plan's `### Build and release`:

- 2026-11-05: Release signing — separate Fontaine-owned minisign keys for `release` and `dev`,
  public keys checked in at `rust/fontaine/keys/` and compiled in, private keys only in the
  `release-signing` (tags, required reviewer) and `dev-signing` (main) GitHub Environments. Every
  archive is signed, published as a draft, re-downloaded and verified, then published. Reason:
  update trust anchored to Fontaine's keys (#175/#176), with a dev-key compromise unable to reach
  `release`.
- 2026-11-05: The dev channel publishes each verified `main` build as prerelease
  `dev-<run_number>`, gated on the repository variable `FONTAINE_DEV_CHANNEL`. Reason: the same
  draft-verify-publish gate as `release`, and no red `main` before the dev key exists.

## Testing Strategy

- **Unit (`release_signature`)**: every `VerifyError` class with disposable keys from the
  `minisign` crate (step 3), and the shipped-key-files test.
- **CI script coverage (`ci.yml` Linux)**: the real CLI and the real scripts run against
  disposable keys for the valid, missing, malformed, wrong-key, tampered, orphan, empty and
  wrong-channel cases. Then the ignored interop test runs on the CLI output. This tier is needed
  because the scripts and the CLI's file format are what actually gate publication, and a unit
  test against the Rust crate cannot exercise them. A failure there is silent: it would publish
  something unverified, or stop all publication.
- `cargo fmt --check`, `clippy -D warnings`, `cargo test` and `cargo deny check` as usual.
  `dist plan` keeps passing on the PR's `plan` job.

## Manual Verification

These run once, after the maintainer bootstraps the keys and environments. They are manual
because they depend on GitHub-side environment settings and real tags, which no test can create.

1. Push a prerelease tag such as `v0.1.0-rc.1`. Expected: the `sign` job waits for approval in
   `release-signing`, then the run ends with a published release in which every archive has a
   `.minisig`.
2. Download an archive and its signature, then run `minisign -Vm <archive> -p rust/fontaine/keys/release.pub`.
   Expected: `Signature and comment signature verified`, with the trusted comment binding
   `channel=release` and the file name.
3. Set `FONTAINE_DEV_CHANNEL=enabled` and merge a PR. Expected: a published prerelease
   `dev-<n>`, with no approval prompt, whose archives verify against `dev.pub` and fail against
   `release.pub`.
4. Open a PR that adds `environment: release-signing` to a job. Expected: the deployment is
   refused by the tag-only rule, and the secret is never exposed.
